# GraphGuard P3 same-event Kafka → analyst acceptance

In the disposable real Kafka/Neo4j CI, one original **synthetic** transaction is published with an identical retry and a malicious same-identity conflicting payload, plus invalid data. The existing real consumer verifies durable local SQLite source receipts, source-ID uniqueness, conflict and invalid-event DLQ, restarted consumer replay, Neo4j user/merchant/device graph topology and matching source SHA-256 hash. The SAME accepted transaction ID and payload SHA is read from the committed source ledger, its point-in-time feature snapshot is verified, and an independently trained **frozen, SHA-256-pinned** Logistic/XGBoost baseline is used to generate a real model probability, a native SHAP explanation, and a signed local analyst case. An unauthenticated case open is blocked. A signed analyst escalates the case, an independently signed admin records review completion, and the append-only HMAC audit head is re-read from SQLite to prove persistence. Source, graph, features, model manifest, native SHAP and final case digest are connected in one CI JSON evidence artifact, without any external API, provider credentials or real customer information.

**Boundaries:** The case endpoint runs through FastAPI TestClient (real ASGI handlers/SQLite, not Chromium); the separately passing local Next.js HTTP smoke tests the frontend. The graph is verified and shares source identity, but the frozen tabular model reads the durable PIT ledger, NOT graph neural-network embeddings or a graph feature query. This is **not live banking fraud**, proof of wrongdoing, multi-tenant production IAM, real historical model accuracy, or a deployed cloud reviewer UI. Human case closure is distinct from automated risk judgement. See [CI integration job](../.github/workflows/ci.yml) and [P2 synthetic calibration](P2_CALIBRATION_DRIFT.md).
